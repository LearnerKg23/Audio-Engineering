# 07 — Stage 4: Semantic Post-Processing & LLM Guardrailing

## 1. Core Objective & Semantic Context

The raw text output from acoustic speech recognition (Stage 3) is inevitably noisy, disfluent, and fragmented:
* Contains phonetic drops from momentary microphone fading or acoustic noise spikes.
* Contains conversational disfluencies: false starts, stuttering, filler words (*"uh"*, *"मतलब"*, *"you know"*).
* Spans mixed scripts (Devanagari mixed with Latin characters).
* Lacks semantic hierarchy, thematic categorization, or executive synthesis.

The objective of Stage 4 is to pass this raw speaker-attributed transcript through a localized foundational Large Language Model (LLM) equipped with rigorous **prompt guardrails** to generate an executive-ready structured intelligence report.

---

## 2. Modular LLM Provider Architecture & Inference Strategy

To balance rapid, agile development with academic fidelity, Stage 4 is architected with a **Modular Provider Pattern** (`BaseLLMProvider`). This decouples the prompt engineering, guardrailing, and Pydantic schema validation layers from the underlying inference backend.

### Modular Provider Structure:
1. **API Endpoints (Development & Iteration Phase)**:
   - Providers: `OpenAIProvider`, `GroqProvider`, or `SarvamProvider`.
   - *Rationale*: Eliminates local VRAM constraints during pipeline integration, enables rapid testing of prompt variations, and allows direct evaluation of state-of-the-art reasoning on code-switched Hinglish.
2. **Local Quantized Models (Optional Milestone & Evaluation)**:
   - Providers: `LocalQuantizedProvider` (Airavata 7B, OpenHathi, or Llama-3-8B via 4-bit `bitsandbytes` or `llama.cpp`).
   - *Rationale*: Preserves the proposal's recommendation of open-weight Indian models without bottlenecking early pipeline engineering.
3. **Provider Swappability**:
   - The active provider is controlled strictly via `configs/llm_guardrails.yaml`:
   ```yaml
   llm:
     provider: "groq" # Options: "groq", "openai", "sarvam", "local_quantized"
     model_name: "llama-3.1-8b-instant"
     temperature: 0.1
     max_tokens: 1024
   ```

| LLM Candidate / Provider | Model Backend | Linguistic Strengths | Operational Role |
|---|---|---|---|
| **Groq / OpenAI API** | Llama-3.1-8B-Instant / GPT-4o-mini | Rapid token generation, strict JSON schema compliance. | Primary development engine for prompt iteration and test suites. |
| **Sarvam AI API** | Sarvam-2B / Localized Models | Specialized Indian language foundational models. | Domain benchmark on regional vernacular and Hinglish idioms. |
| **Airavata (AI4Bharat)** | 7B Open-Weight Llama-2 Fine-tune | Aligned on 22 Indian languages and Hinglish. | Optional local/Colab evaluation comparator. |

## 3. Prompt Engineering & Guardrailing Architecture

Unconstrained LLM generation on conversational transcripts is notoriously susceptible to **hallucination**: inventing numbers, extrapolating facts not mentioned, or misattributing statements to the wrong speaker.

To prevent this, our prompt framework incorporates **Four Structural Guardrails**:
1. **Source Grounding (Negative Constraint)**: *"You are an objective computational analyst. Extract and clean only what is explicitly stated in the transcript. Never assume, infer, or extrapolate facts, numbers, or intentions not present in the text."*
2. **Attribution Integrity**: *"Preserve the exact speaker attribution (`SPEAKER_00`, `SPEAKER_01`). Never merge or switch statements between speakers."*
3. **Phonetic Repair without Content Invention**: *"Repair phonetic artifacts and conversational stuttering into grammatically smooth text while strictly preserving the speaker's original meaning and regional vocabulary."*
4. **Deterministic JSON Schema Enforcement**: The LLM must output valid JSON conforming strictly to Contract 5 (`final_report.json`).

### Master Prompt Template (`src/llm/prompts/post_processing_prompt.jinja`)
```markdown
[SYSTEM]
You are a senior computational linguist and intelligence analyst specializing in Indian regional languages and code-switched dialogues (Hinglish/Benglish).

You will receive a raw, speaker-attributed transcript generated by an Automatic Speech Recognition (ASR) system. Your task is to clean, synthesize, and structure this transcript.

RULES AND CONSTRAINTS:
1. STRICT TRUTHFULNESS: Do not invent any names, numbers, crop prices, or facts. If a segment is marked [Unintelligible], do not guess its meaning.
2. PRESERVE SPEAKER ROLES: Maintain absolute speaker distinction. Never attribute Speaker A's remarks to Speaker B.
3. CODE-SWITCHING HANDLING: Smooth out conversational disfluencies while preserving natural code-switched technical terms (e.g., "MSP", "mandi rate", "price").
4. OUTPUT FORMAT: Output valid JSON matching the exact schema provided. Do not include markdown code block wrappers or explanations.

[INPUT TRANSCRIPT]
{{ raw_transcript_json }}

[TARGET JSON SCHEMA]
{
  "executive_summary": "string (concise 3-4 sentence synthesis)",
  "primary_topics": ["string"],
  "keyword_tags": ["#Tag1", "#Tag2"],
  "key_findings": [
    {"topic": "string", "detail": "string", "speaker_attribution": "string"}
  ],
  "speaker_separated_dialogue": [
    {"speaker": "string", "timestamp": "string", "cleaned_text": "string"}
  ]
}
```

## 4. Evaluation Metrics for Semantic Processing

To prove that the LLM stage adds measurable value rather than superficial rewriting, we implement quantitative NLP metrics:

### 1. Factual Consistency & Hallucination Check
An automated audit script that extracts all named entities, monetary figures, and dates from the LLM `executive_summary` and validates their presence in the `raw_transcript`:
$$\text{Hallucination Rate} = \frac{\text{Entities in Summary not found in Raw Transcript}}{\text{Total Entities in Summary}}$$
*Target*: $0.0\%$ (Zero tolerance for invented numerical rates or claims).

### 2. Lexical & Semantic Overlap (ROUGE & BERTScore)
* **ROUGE-L**: Measures longest common subsequence overlap between reference summary and generated summary.
* **BERTScore**: Computes semantic embedding similarity using multilingual contextual embeddings (`xlm-roberta-base`), ensuring conceptual fidelity even when phrasing is cleaned.

### 3. Transcript Cleaning Fidelity (Fluency vs. Distortion)
* Character Edit Ratio between raw and cleaned transcripts to quantify disfluency reduction without semantic drift.
